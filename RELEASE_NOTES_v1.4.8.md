# ProxCenter v1.4.8

**vDC storage policies and tenant VLAN networks.** A provider now governs tenant storage with QoS caps and per-tier quotas, and hands each vDC its own VLAN ranges to build networks in, self-service. Alongside them: a Task Center that shows every job, warm migration nodes prepared by the product itself, and a large batch of Site Recovery, migration and access control fixes.

## Multi-tenant and vDC

- **Storage policies with QoS caps and per-tier quotas.** A provider declares a policy on a connection and one of its storages, sets read and write IOPS and bandwidth caps and a quota for that tier, then assigns policies to vDCs. The caps are stamped on the disks a tenant creates, deploys, clones, restores, rolls back, imports or moves, and the per-tier usage is metered from the storage content listing rather than from the declared size, so an `import-from` allocation is counted for what PVE really allocates. Existing disks can be brought under a policy in one action with live progress, and a governed-disks expander flags the ones that drifted. The deploy wizard is gated on the tier quota instead of failing on the last step.
- **Tenant VLAN networks with provider-managed pools.** A provider hands each vDC one or more VLAN ranges and a shared SDN zone; the tenant then creates its own networks inside those ranges, self-service, with the tag allocated from its pool. VXLAN allocation is floored at VNI 10000 so a VLAN tag can never collide with it, and external addressing is offered on VLAN networks only.
- **Optional VMID ranges extended to vDC tenants.** The restriction to MSP tenants was purely application side. A vDC tenant on a shared provider cluster can now carry a range, with the used-VMID scan resolved through its vDCs so uniqueness and the next free id stay correct across tenants on the same cluster. No migration: the columns have existed since v1.4.7.
- **The VMID range is a column of the tenants table**, sorted on the lower bound.

## Task Center

- **Migrations are visible and cancellable.** The page aggregated the four orchestrator sources and never the migration jobs table, so the Migration filter it offered could never match anything. Migration jobs join as a fifth source, scoped by target connection so a vDC tenant sees its own migrations even though it does not own the source hypervisor connection.
- **Recovery plan executions are reported as Site Recovery** instead of being filed under maintenance.
- **Logs are fetched for every type**: rolling updates and replication from the orchestrator, migrations from the shared task history, DRS from the PVE task log rebuilt out of the UPID, and Site Recovery synthesized from the per-VM results.
- **Actions are routed per type**, a migration cancellation is confirmed, action errors are surfaced, and the buttons the orchestrator cannot honour are gone. Deleted connections are named instead of printing a raw id.
- **The ProxCenter tab of the taskbar carries the same jobs over the whole history**, and a double click opens the Task Center.

## Migration

- **The product prepares a warm-migration node itself.** Broadcom closed the public VDDK download in August 2026: the portal URL our node-setup guide pointed at returns 404 for everyone, signed in or not. The VDDK now ships through a private registry package, and the migrate dialog gains a "Prepare the node" action that installs nbdkit, nbd-client and the nbdkit VDDK plugin, enables the Debian non-free component, unpacks the VDDK, adds the symlink the nbdkit shipped with Proxmox 9 needs and loads the nbd module. Every step is idempotent, and the manual guide stays as the fallback for a node without registry egress.
- **The operator chooses the cutover moment.** A warm migration used to switch over as soon as the projected downtime fitted its budget. In manual mode the run keeps issuing delta passes, paced at one per minute, with no expiry, until the operator asks for the switchover or cancels, and the downtime shown at the moment of the click is the real one. The switchover and cancel controls are the same component in the VM panel and in the migrate dialog.
- **A refused guest shutdown is recoverable.** The cutover asked the guest to shut down and then polled in silence for five minutes; a guest that refused cost the whole transfer. The wait is now a step of its own, it restates the time left every minute, and it offers a hard power off, which stays the operator's decision because it makes the final delta crash-consistent. The budget grows to 30 minutes, and a host that refuses the hard power off, as an ESXi licence restriction does, is logged instead of crashing the job. vSphere SOAP faults now carry the concrete fault type and message instead of the generic wrapper.
- **The downtime budget is settable from the migrate dialog**, as a curated slider paired with an exact seconds field, over the 30 s to 24 h range the API enforces.
- **virt-v2v never prompts for the root filesystem.** The conversion is launched detached, so an interactive `--root ask` prompt died on end of file after the whole transfer had completed. This is not limited to dual-boot guests: a btrfs guest with snapper snapshots inspects as one system per subvolume, and the reported guest listed sixteen candidates. Conversion now runs with stdin closed, drops snapshot subvolumes from the candidate list and retries once with an explicit root, and parks the job for an operator choice when several real systems remain. A root filesystem can also be pinned up front in the dialog.
- **A cancelled job that was parked really stops.** The virt-v2v cancel registry was never wired into the cancel route, so the row changed state while the pipeline kept waiting.
- **A failed create no longer destroys a pre-existing VM.** The VMID is reserved before the guest exists, so a failure in between made the cleanup call DELETE on a VMID it had never created, and with a user-supplied id that was already taken it purged the guest holding that id. Destruction now happens only when the job actually created the VM.
- **A slow storage listing no longer empties the Target Storage field.** A datacenter declaring many PBS storages needs 20 s or more to answer, well past the 8 s budget that was hardcoded in two literals. Both budgets are now settings, the storage listing opts into the long one by intent, the dialog surfaces the server reason with a retry instead of swallowing it, and a response timeout no longer trips the failover circuit breaker like an unreachable host.
- **VMID availability is scoped to the target connection.** With two clusters connected, cloning a template was impossible: the dialogs were fed the merged inventory of every connection, so an id used on the second cluster was refused on the first. Proxmox only requires uniqueness inside a cluster. MSP and vDC tenants keep their cross-cluster range, which is an explicit contract enforced server side.

## Site Recovery

- **A powered-off VM can be replicated.** Replication is pure Ceph RBD and the only power-dependent step is already guarded per VM, yet the create-job dialog and the API route both filtered on the running state. Worse, on a tag-based job a guest that was powered off was silently dropped from the protected set at the next re-resolution while the job kept reporting success. Tag resolution no longer looks at power state, every VM that leaves or joins the protected set is logged, and the per-VM rows that no longer belong are pruned. Templates stay excluded, since a replica of one could not start at failover.
- **A tag-based job matching nothing says so.** It lands in an explicit `no_match` status instead of the error and retry path: no failure mail, the next sync stays scheduled, and the status is rendered on the protection chip and filter, the emergency DR chip and the dashboard job distribution. RPO alerts deliberately keep firing, because a job protecting nothing must keep nagging.
- **The boot screenshot delay is a test failover option.** The stabilization wait before the console capture was a constant 45 s, so a guest that boots slower was photographed mid-boot. The delay rides in the request, from 5 to 600 seconds, is persisted on the execution and drives the existing countdown. Executions recorded before the column existed keep the 45 s default.
- **A DR test can leave the NICs connected.** The orchestrator already knew how, the frontend always asked for isolation. It is now a switch, on by default, with a warning about colliding production addresses, and the mode the run used stays visible on a chip.
- **Replication RPO and Ceph OSD latency alerts.** Thresholds could only describe how full a resource was. Three types join them: a job whose last successful sync fell behind its own RPO target, a job that failed outright, and an OSD answering slower than the operator tolerates. The RPO grace is a percentage of each job's own target rather than a fixed delay, since ten minutes late is harmless against a 24 h target and unacceptable against a 15 min one. The OSD check ships disabled, because no latency threshold suits every disk and an upgrade must not start alerting on its own. An OSD that is down is left out of the reading rather than measured at zero.
- **A cleared alert sends a recovery notification**, carrying when it fired, when it cleared, how long it lasted and the value it came back to. It bypasses the minimum severity filter, since a recovery ranks below any threshold and would otherwise be dropped in silence. Resolution now waits for hysteresis, so a value oscillating around its threshold no longer mails once a minute, and both knobs, the margin and the number of confirmations, are exposed in the alert thresholds screen. Stale snapshot alerts can finally resolve: a deleted snapshot never comes back through the checker, so its alert stayed active for ever.
- **Alert mails keep the severity the engine established.** The notifier re-derived it from value against threshold, so an alert with no measured quantity, a failed replication job for instance, was always classed as a warning and never reached an operator whose minimum severity is critical.

## Access control and security

- **Community installs grant the super-admin role again.** Since v1.4.7, an account created from Settings > Security > Users on a Community install received no RBAC grant at all: the auto-grant was gated on a resolved licence verdict, which a Community install running the frontend alone can never establish. Its owner saw an empty dashboard, and the operator could not repair it because the role picker is Enterprise gated. The gate now keys on the deployment shape, a sign-in backfill repairs the accounts already created without a grant, LDAP provisioned ones included, and both cases the original change closed stay closed.
- **API tokens: offboarding, scope audit and real deletion.** Disabling or deleting a user left the tokens they had minted behind with no way to see them; the user dialogs now list them and offer to delete them in the same gesture, unchecked by default, with the deletion running before the account write. The creator is frozen on the token so provenance survives the account being deleted. Deleting a token now removes the row instead of stamping it revoked, which had left legacy revoked tokens stuck in the table. The `compliance:read` scope, which mapped to a write-capable permission and granted nothing today, is gone, and the scope test now fails on any scope mapping a dangerous or non-read permission.
- **A pool or tag scoped user can create a guest.** A grant whose only scope is flat can never satisfy a connection-scoped check, so six of the routes the Create VM wizard calls refused it: the pool and storage pickers came back empty and the submit was denied. Such a caller now gets a perimeter derived from the guests they already see on one connection, nothing wider than what the inventory stream already sends them, and creation forces the accessible pool so a guest cannot be created invisible to its own creator.
- **Two unguarded routes.** Creating an alert now requires `alerts.manage`, checked before the body is read, like the other writes on the resource. Upload progress is scoped to the user who opened the transfer, so the upload id is no longer the only thing standing between a signed-in user and someone else's counters.
- **An unparseable branding colour no longer turns every page into a 500.** A White Label primary colour typed without its leading `#` was stored as is and handed to MUI, which throws on anything it cannot parse, in a provider that wraps the dashboard and the login page alike. The value is normalised on the way in and on the way out, the field explains the expected format and blocks Save, and both branding reads repair what is already stored, so an instance stuck on the 500 page recovers on its own after the update instead of needing a database edit.
- **The orchestrator no longer trusts `X-Forwarded-For` blindly** on every request, where any caller could pick the IP it was recorded as (GO-2026-5777), and it builds on a Go toolchain that still receives patches.
- **CVE-2026-40345**: a `deepmerge-ts >= 8.0.2` floor, since the vulnerable version is pinned exactly by `@prisma/config` and no Prisma release ships the fix yet.

## Monitoring and inventory

- **Disk health.** SMART attributes are shown when a disk row is expanded, including the NVMe text form PVE returns on real hardware, parsed into labelled rows whose direction is explicit so remaining life is never coloured like consumed life. An unrecognised health string, `UNKNOWN!` included, is no longer painted green.
- **ZFS pool state, scrub and vdev tree** on the node view, with the wearout bar gradient fixed: it read backwards, so a barely worn disk showed red.
- **Node temperatures.** Proxmox exposes none, and a stock node has neither lm-sensors nor ipmitool, so the readings are read from the kernel hwmon tree over SSH, aggregated per role with a threshold per role. A node with nothing to report answers with an explicit unavailable rather than an error. Each figure sits next to what it measures, and the root filesystem usage bar joins the same column, labelled for what it is: the host root, not the datastores.
- **A ZFS ARC dashboard widget.** ARC was only visible overlaid on memory available in the node summary, where three orders of magnitude flatten it onto the baseline. The widget gives ARC its own auto scaled axis plus a percentage view, excludes the nodes that report none, and names the PVE 9 requirement rather than showing an empty frame.
- **The real disk format is reported.** PVE deletes the optional `format=` property right after allocating a volume, so falling back to raw mislabelled every qcow2 and vmdk disk; the format is derived from the volume name instead. Which formats a storage accepts stopped being a function of its type in PVE 9, so both storage routes compute it from the cluster storage config and the four disk dialogs follow that answer.
- **The Cloud-Init drive is labelled as such.** It is a `media=cdrom` entry backed by a real volume, so it appeared as a CD-ROM on a block storage, and opening the ISO editor on it would have detached the volume.
- **A slow RAM hotplug no longer reports a failed save.** Removing memory unplugs one DIMM at a time and PVE sleeps 3 s per module, so dropping a running guest from 8G to 4G costs 24 s at best, well past the request budget: the write aborted on our side while PVE went on applying it. Guest config writes now go through the asynchronous PVE handler and follow the task, a response timeout on a write no longer counts towards the failover threshold, and the saved message follows the pending keys PVE reports instead of the power state, so a hotplugged change reads as applied and a pending one names the stop and start it needs.

## Backups

- **Pool-based selection for backup jobs.** The API layer already mapped the pool mode, resolved its members and read it back; only the job dialogs never offered the choice. A job can now follow a Proxmox resource pool, fed by the pools endpoint so a scoped caller sees its own perimeter, and the inventory panel resolves the pool instead of showing a dash.
- **The PBS token guidance is correct.** `DatastoreReader` alone does not cover read-only monitoring: without `Audit`, server status, services, disks and update information stay empty. The setup guide now recommends both, and the guide also documents the `Admin` ACL a token needs for vDC backup binding.
- **A PBS server declared by IP keeps working on Node 26**, which throws on an SNI over an IP address: the TLS fingerprint is captured without it.

## Interface

- **Widgets stay where they are dropped.** The dashboard grid is configured with a no-compaction compactor, since the v1 `compactType` prop is silently ignored by react-grid-layout v2, and a display-only row reclaim keeps collapsed sections and scope filtering working. A new theme-logo widget shows the branding logo, the ProxCenter logo or the theme badge.
- **The colour scheme is stored in the user account**, per tenant and per user, resolved server side so the restored palette is already in the first HTML. An existing cookie is imported once, carrying the id of the account that wrote it so a shared browser never copies one person's look into another's.
- **Text stays readable on a light branding colour.** Two theme overrides bypassed the contrast text MUI computes, so labels and initials kept their own colour on a primary filled surface, which is what the command palette and the profile button showed.
- **Presentation fixes.** The tooltip hover band on bar charts follows the theme instead of painting a white block over the hovered bar in dark mode, the tree context menus share one paper with theme-aware icons, the disk tables use the product typography instead of hardcoded monospace, and three list items no longer nest a block element under a paragraph.

## Dependencies and build

Eight Dependabot updates batched, including Next 16.3 and MUI X Data Grid 9.12, plus `concurrently` 10 verified against a real dev server, and the earlier batches of thirteen and five updates. Next 16.3 makes the build type check fatal on the TypeScript 6 `baseUrl` deprecation and on the full tsconfig scope, so the build now points at a dedicated `tsconfig.build.json` that excludes tests while the editor and plain `tsc` keep checking everything. CI runs on Node 26 and the package declares its Node floor.

## Upgrading

Pull the images. Four schema migrations ship with this release, applied by the frontend entrypoint at first boot under an advisory lock: the user appearance preferences table, the API token creator provenance column, the vDC VLAN support tables and the vDC storage policy tables.
